## How a schema is read

The message is one GeoJSON Feature. The wire addresses the Point coordinates, top-level
members and one level of `properties`; so scalar members there are `field` lines and
everything else (nested objects, arrays, booleans) is residue, which the geojson wire
carries back as it was (engine-spec 0.1, ruling 13 of 0.6).

## Evidence for the shared keys

- `lon`, `lat`, `hae` (`geometry` of type Point): JSON-FG keeps `geometry` as in GeoJSON: the
  requirements class depends on IETF RFC 7946, and a geometry that is not in WGS 84 goes in
  `place`, not `geometry`. RFC 7946 section 4 gives WGS 84 longitude and latitude in decimal
  degrees and an optional height in metres above the WGS 84 ellipsoid.

## What is not carried

- **`time`, `place`, `measures`** are top-level objects, and `featureType` and `featureSchema`
  are top-level members other than `id`; the geojson wire addresses none of them (top-level
  residue is not settled). The instant of `time` is bound to `time_ms` in
  `ogc-jsonfg-feature-json`, which reads the same Feature on the json wire.
- **`id`** is a number or a string; no transform reads either, so `uid` is not bound.
- **`place`** is not bound to a position: it holds a geometry in the CRS that `coordRefSys`
  names, which the pack cannot check; only when that CRS is WGS 84 would it be the same
  meaning.

## Keys and lists

list name comes first). Names are pinned in `tools/gen/names/ogc-jsonfg-feature.json`: a later run keeps every

## Vectors

One same-format round trip per kind, computed by the generator's own json codec (no engine):
every mapped place holds a value, an array has two items (one inside an item), the input is
canonical, so the expected output is the input.

`packs/geojson/vectors/gen-geojson-to-ogc-jsonfg-feature.json`: from the input of an existing hand-written `geojson` vector. Carried: `lat`, `lon`, `hae`. Not carried: `uid`, `type`, `time_ms`, `how`, `ce`, `le`, `callsign`.
