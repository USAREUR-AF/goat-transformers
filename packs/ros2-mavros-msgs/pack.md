# ros2-mavros-msgs

ROS 2 `mavros_msgs` messages as the JSON of a rosbridge `publish` operation. Generated by
`tools/gen/ros2msg2pack.py` from the .msg files of the package (and the files
they refer to); do not edit by hand, run `tools/gen/ros2-run.sh`.

## Why the `json` wire

Inside ROS 2 a message is serialized as CDR by the middleware (and stored so by
rosbag2). A program outside ROS most often meets it as the JSON that rosbridge
publishes. rosbridge writes a message as one JSON object: each field a member
under its .msg name, a nested message an object, an array a JSON array,
`uint8[]` and `char[]` a base64 string (protocol section 3.1),
`builtin_interfaces/Time` and `Duration` an object `{sec, nanosec}`, and a float
that is NaN or infinite `null`. Every one of those maps to the `json` wire
(engine-spec 0.5, 0.7) with no addition to the pack language, for every message
of the package. CDR on the `bits` wire is not written: a CDR payload carries no
type, so no `when` can tell one message from another and each message would be
a format of its own; and a message with a string or an unbounded array places
every later field at an offset that depends on that length and its alignment,
which `layout sequential` has no line for (`align` is relative to the field
before it, not to a variable start).

## Message convention

A message is one rosbridge `publish` operation (protocol v2.1.0, section 4.3.3)
that carries the optional `type` member in the full notation of section 4.1:

```
{"op":"publish","topic":"<topic>","type":"mavros_msgs/msg/<Name>","msg":{<message>}}
```

- `op` must be `publish` (a common `when`); it is written on encode.
- `type` selects the kind; it is written on encode. The short notation
  `mavros_msgs/<Name>`, which rosbridge also accepts, selects no kind (`no-kind`).
  A `publish` the server sends to a subscriber has no `type`: the receiver adds
  it from its subscription before decoding.
- `topic` is the raw key `ros2mavros.topic`.
- Other members of the operation (`id`, `qos`, `latch`, `queue_size`) and any
  member of `msg` the pack does not map are residue when they are scalars or
  objects of scalars, and are written back after the mapped members.
- On encode for an entity from another format, the kind is the first, in the
  order below, whose `requires` keys the entity holds. Each kind requires its
  first key (a message with no field requires `ros2mavros.topic`).

## Shared-model keys

The positions of `mavros_msgs/msg/HomePosition`, `GPSRAW` and `GPSINPUT` are bound to
`core` keys. The other position fields of the package are not, for the reasons below.

| Wire field | Model key | Evidence | Note |
|---|---|---|---|
| `msg.geo.latitude` | `lat` (deg, WGS 84) | HomePosition.msg: "geographic_msgs/GeoPoint geo # geodetic coordinates in WGS-84 datum"; GeoPoint.msg: "Latitude [degrees]" | same frame and unit |
| `msg.geo.longitude` | `lon` (deg, WGS 84) | as above; GeoPoint.msg: "Longitude [degrees]" | same frame and unit |
| `msg.geo.altitude` | `hae` (m above the WGS 84 ellipsoid) | GeoPoint.msg: "Altitude [m]. Positive is above the WGS 84 ellipsoid". mavros's `mavros/src/plugins/home_position.cpp` (listed in `PROVENANCE.md`) fills it from the MAVLink altitude in millimetres above mean sea level plus the geoid-to-ellipsoid height | ellipsoidal height |

| `GPSRAW` `msg.lat`, `msg.lon` (int32) | `lat`, `lon` with `scale:1/10000000` | GPSRAW.msg: "[degE7] Latitude (WGS84, EGM96 ellipsoid)", "[degE7] Longitude (WGS84, EGM96 ellipsoid)" | degrees times 10^7; `scale` (engine-spec 0.15) turns the integer into degrees |
| `GPSRAW` `msg.alt_ellipsoid` (int32) | `hae` with `scale:1/1000` | GPSRAW.msg: "[mm] Altitude (above WGS84, EGM96 ellipsoid). Positive for up." | millimetres to metres |
| `GPSINPUT` `msg.lat`, `msg.lon` (int32) | `lat`, `lon` with `scale:1/10000000` | GPSINPUT.msg: "[degE7] Latitude (WGS84, EGM96 ellipsoid)", "[degE7] Longitude (WGS84, EGM96 ellipsoid)" | as GPSRAW |

Kind `home_position` requires `lat lon`. Kinds `gpsinput` and `gpsraw` also require
their own `fix_type`, so an entity from another format with only a position is still
encoded as `home_position`, as before these bindings.

A value decoded through `scale` is the nearest double to the integer times 1e-7; it
encodes back to the same integer for most values, and an encoder writes the quotient
as a JSON number, which for a value that is not exact can carry a fraction (a reader
that wants an integer rounds it).

Not bound, and why:

- `GPSRAW.alt` and `GPSINPUT.alt` are above mean sea level, not the ellipsoid.
- `GlobalPositionTarget.latitude`/`longitude` and `ADSBVehicle.latitude`/`longitude`
  state no datum in the .msg, and their altitudes are "AMSL or above terrain" and
  "AMSL". Raw keys.
- `Waypoint.x_lat`/`y_long`/`z_alt` depend on the `frame` field (global, relative
  or local); one binding cannot hold for every frame. Raw keys.
- `OpenDroneIDSystem` operator position: integers in 1e-7 degrees with no datum stated
  in the .msg. Raw keys.

## Validity flag not applied

GPSINPUT and GPSRAW: `fix_type` 0 is no GPS and 1 no position information (GPSINPUT.msg, GPSRAW.msg). The pack keeps the flag as a raw key and binds the position whatever it says: a message whose
flag says there is no fix converts with the coordinates it carries (often 0, 0), as if they were a
position. The pack language has no gate for a JSON or protobuf member yet (asked of gt-lang); until
it has, a consumer must read the flag. Bit-level packs of the same messages (PX4) read the shared
keys only when the flag says so.

## Not mapped, and why

| What | Why |
|---|---|
| Constants (`uint8 STATUS_FIX = 0` and the like), 502 in this package | the pack language has no line that names a constant of a field; the value of the field is carried as a number |
| Default values in the .msg (none in this package) | not written on encode: rosbridge fills a field the `msg` omits with its default (protocol 4.3.3), so an absent key needs no value |
| Length of a fixed array and bound of a bounded one (ActuatorControl.controls float32[8], HilActuatorControls.controls float32[16], LandingTarget.angle float32[2], LandingTarget.size float32[2], Mavlink.payload64 uint64[<=33], Mavlink.signature uint8[<=13], OnboardComputerStatus.cpu_combined uint8[10], OnboardComputerStatus.cpu_cores uint8[8], OnboardComputerStatus.fan_speed int16[4], OnboardComputerStatus.gpu_combined uint8[10], OnboardComputerStatus.gpu_cores uint8[4], OnboardComputerStatus.link_rx_max uint32[6], OnboardComputerStatus.link_rx_rate uint32[6], OnboardComputerStatus.link_tx_max uint32[6], OnboardComputerStatus.link_tx_rate uint32[6], OnboardComputerStatus.link_type uint32[6], OnboardComputerStatus.storage_total uint32[4], OnboardComputerStatus.storage_type uint32[4], OnboardComputerStatus.storage_usage uint32[4], OnboardComputerStatus.temperature_core int8[8], OverrideRCIn.channels uint16[18], StatusEvent.arguments uint8[40], TerrainData.data int16[16], Trajectory.command uint16[5], Trajectory.point_valid uint8[5], Trajectory.time_horizon float32[5], Tunnel.payload uint8[128], Vibration.clipping float32[3]) | a `json` group has no `count` (engine-spec 0.7); any number of items decodes and encodes, and a sender that writes another number is not refused |
| `uint64` values above 2^63-1 | a model `int` is a 64-bit signed integer (engine-spec 0.5 ruling 2); such a value is outside it |
| NaN and infinite floats | rosbridge writes them `null`; `null` is absent (engine-spec 0.5), so the key is absent and nothing is written back |
| `uint8[]` and `char[]` sent as a list of numbers | rosbridge accepts that from a client (protocol 3.1) but writes base64; the pack reads the base64 string only, and a list there is `transform-decode` |
| Members inside an array item that the .msg does not define | engine-spec 0.7: items carry no residue |
| `msg` of a message with no field (CommandCode) | encode writes no `msg` member, because a nested object with no members is not written (engine-spec 0.5); rosbridge requires `msg` |
| PNG, CBOR and fragment encodings of the protocol (sections 3.2 to 3.5) | other byte forms of the operation; the pack reads JSON text |
| `ParamEvent.value.byte_array_value` (`byte[]`) | the protocol states no JSON form for byte[] (only uint8[] and char[] become base64), and rosbridge's converter at this commit copies the octet sequence as a list of one-byte objects, which its JSON writer cannot write |

## Vectors

`vectors/gen-rt-<kind>.json`: one round trip per kind, every field of the
message present, two items in each unbounded array outside a group and one
inside, the stated number in a fixed or bounded one, and an `id` member as
residue. `gen-edge-*` and `gen-err-*` are edge and error cases, each naming the
rule it rests on in `source`; `gen-x-*` convert to geojson. 86 vector files.
`packs/geojson/vectors/gen-geojson-to-ros2-mavros-msgs-*.json` convert from geojson.
Expected text is written by the generator from the .msg field order and checked
by its own json-wire codec; no engine produced it.
