# ros2-marti-nav-msgs

ROS 2 `marti_nav_msgs` messages as the JSON of a rosbridge `publish` operation. Generated by
`tools/gen/ros2msg2pack.py` from the .msg files of the package (and the files
they refer to); do not edit by hand, run `tools/gen/ros2-run.sh`.

## Why the `json` wire

Inside ROS 2 a message is serialized as CDR by the middleware (and stored so by
rosbag2). A program outside ROS most often meets it as the JSON that rosbridge
publishes. rosbridge writes a message as one JSON object: each field a member
under its .msg name, a nested message an object, an array a JSON array,
`uint8[]` and `char[]` a base64 string (protocol section 3.1),
`builtin_interfaces/Time` and `Duration` an object `{sec, nanosec}`, and a float
that is NaN or infinite `null`. Every one of those maps to the `json` wire
(engine-spec 0.5, 0.7) with no addition to the pack language, for every message
of the package. CDR on the `bits` wire is not written: a CDR payload carries no
type, so no `when` can tell one message from another and each message would be
a format of its own; and a message with a string or an unbounded array places
every later field at an offset that depends on that length and its alignment,
which `layout sequential` has no line for (`align` is relative to the field
before it, not to a variable start).

## Message convention

A message is one rosbridge `publish` operation (protocol v2.1.0, section 4.3.3)
that carries the optional `type` member in the full notation of section 4.1:

```
{"op":"publish","topic":"<topic>","type":"marti_nav_msgs/msg/<Name>","msg":{<message>}}
```

- `op` must be `publish` (a common `when`); it is written on encode.
- `type` selects the kind; it is written on encode. The short notation
  `marti_nav_msgs/<Name>`, which rosbridge also accepts, selects no kind (`no-kind`).
  A `publish` the server sends to a subscriber has no `type`: the receiver adds
  it from its subscription before decoding.
- `topic` is the raw key `ros2martinav.topic`.
- Other members of the operation (`id`, `qos`, `latch`, `queue_size`) and any
  member of `msg` the pack does not map are residue when they are scalars or
  objects of scalars, and are written back after the mapped members.
- On encode for an entity from another format, the kind is the first, in the
  order below, whose `requires` keys the entity holds. Each kind requires its
  first key (a message with no field requires `ros2martinav.topic`).

## Shared-model keys

The `wgs84` point of `marti_nav_msgs/msg/Wgs84Sample` is bound to `core` keys. The
evidence is the comment text of `Wgs84Sample.msg` at the commit in `PROVENANCE.md`,
in this project's words:

| Wire field | Model key | Evidence |
|---|---|---|
| `msg.wgs84.y` (float64) | `lat` (deg, WGS 84) | the file names the point a WGS-84 measurement and gives its y as latitude in decimal degrees |
| `msg.wgs84.x` (float64) | `lon` (deg, WGS 84) | the same comment gives x as longitude in decimal degrees |
| `msg.wgs84.z` (float64) | `hae` (m over the WGS 84 ellipsoid) | the same comment gives z as the altitude over the reference ellipsoid in metres |

The sample pairs that measurement with the vehicle's local odometry position, so the
point is where the vehicle was. Kind `wgs84_sample` requires `lat lon`.

Not bound: `odom` (a local frame), `wgs84_covariance` (a covariance, not an error
radius), and `header.stamp` (ROS time, which may be simulation time). No other
message of the package states a WGS 84 position: `RoutePoint` holds a pose and the
path messages hold points, all with no geodetic frame stated.

## Not mapped, and why

| What | Why |
|---|---|
| Constants (`uint8 STATUS_FIX = 0` and the like), 3 in this package | the pack language has no line that names a constant of a field; the value of the field is carried as a number |
| Default values in the .msg (none in this package) | not written on encode: rosbridge fills a field the `msg` omits with its default (protocol 4.3.3), so an absent key needs no value |
| Length of a fixed array and bound of a bounded one (PoseWithCovariance.covariance float64[36], TrackedObject.linear_acceleration_covariance float64[9], TwistWithCovariance.covariance float64[36], Wgs84Sample.wgs84_covariance float64[9]) | a `json` group has no `count` (engine-spec 0.7); any number of items decodes and encodes, and a sender that writes another number is not refused |
| NaN and infinite floats | rosbridge writes them `null`; `null` is absent (engine-spec 0.5), so the key is absent and nothing is written back |
| `uint8[]` and `char[]` sent as a list of numbers | rosbridge accepts that from a client (protocol 3.1) but writes base64; the pack reads the base64 string only, and a list there is `transform-decode` |
| Members inside an array item that the .msg does not define | engine-spec 0.7: items carry no residue |
| PNG, CBOR and fragment encodings of the protocol (sections 3.2 to 3.5) | other byte forms of the operation; the pack reads JSON text |

## Vectors

`vectors/gen-rt-<kind>.json`: one round trip per kind, every field of the
message present, two items in each unbounded array outside a group and one
inside, the stated number in a fixed or bounded one, and an `id` member as
residue. `gen-edge-*` and `gen-err-*` are edge and error cases, each naming the
rule it rests on in `source`; `gen-x-*` convert to geojson. 21 vector files.
`packs/geojson/vectors/gen-geojson-to-ros2-marti-nav-msgs-*.json` convert from geojson.
Expected text is written by the generator from the .msg field order and checked
by its own json-wire codec; no engine produced it.
