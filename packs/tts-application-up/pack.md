## Repeated fields

A `repeated` field is a `group` block and a list of module `ttsapplicationup` (engine-spec 0.7). The block's
path is the field-number path of the repeated field from the scope the block stands in: the
message for a block of a kind, one item for a block inside another block. Paths of the lines
inside a block start at the item.

- A repeated message: each occurrence is an item. Its fields are the block's `field` lines, a
  repeated field inside it is a nested block. An item has no residue: a field of the item
  that no line maps is dropped on decode, so only an item whose every field is mapped comes back
  byte for byte.
- A repeated string, number, bool or enum: a block with one line, `field <key> . <transform>`.
  With `pvarint`, `psint`, `pdouble` and `pfloat` decode accepts one occurrence per value and the
  packed form, and encode writes the packed form; `pstring` is one occurrence per item. A message
  that arrives unpacked therefore leaves packed: the same values, other bytes.
- A list is named as a field at its place would be. A list inside an item, and every key of an
  item, is named from the item's message type and the path inside the item, so every list of
  one message type holds the same keys; where that name is the key the same schema field
  has outside any group, the item uses that key. Names are pinned in the names file under
  `<path>[]`, `<message>:<path in the item>` and `<message>:<field>[]item`.
- No key of an item is bound to a `core` or `track` key.
- `requires` of a kind whose only content is repeated names a list of the kind: it holds when
  the list has at least one item.

## About these The Things Stack messages

The Things Stack (v3) is an open-source LoRaWAN network server. Its Application Server
hands every event of an end device to the application as one `ApplicationUp`: an uplink
(decoded, or normalized), a join accept, the fate of a queued downlink (acknowledged,
not acknowledged, sent, failed, queued, queue invalidated), a solved location, or data
from an application package. Each of those is one kind of `tts-application-up`. The
application sends downlinks back as one `ApplicationDownlink` (`tts-application-downlink`)
or a list of them (`tts-application-downlinks`), to push to or replace the queue.

A message of these packs is one protobuf message. The MQTT, webhook and Pub/Sub
integrations usually carry the same message as JSON in the protobuf JSON mapping; that
form is not a pack. The topic or path that names the event is left to the caller.

## Evidence for the shared keys

`lat` and `lon` are bound in the kind `location_solved` only, at field-number paths
11.2.1 and 11.2.2 (`ApplicationLocation.location`, a `Location`). In `metadata.proto`
the field comment of `Location.latitude` gives it in degrees from -90 to +90, zero at the
equator and positive to the north; the one of `Location.longitude` gives degrees from
-180 to +180, zero at the Greenwich meridian and positive to the east. The files name no
datum; the packs take these degrees as the WGS 84 latitude and longitude of `core`, as
the GNSS receivers and LoRa geolocation solvers that fill the field report them. A person
reviewing the pack may decide otherwise.

Not bound, and why:

- `Location.altitude` is an integer in metres above mean sea level, not above the
  ellipsoid: a raw key, not `hae`.
- The `location` of each gateway in the receive metadata (`rx_metadata`) and the
  `locations` map of an uplink are the gateways' or other sources' positions, not the
  device's, and stand in a list or a map: raw keys or not carried.
- `received_at` is when the server received the event, not when the device measured
  anything: a raw key.

`bytes` fields (the frame payload, keys and session key identifiers) are not carried,
and neither are the fixed-width integers; no protobuf transform reads them.
`google.protobuf.Struct` objects (the decoded payload) and other maps are not addressed
by key. Option imports (`validate`, `thethings/flags`, `thethings/json`,
`protoc-gen-openapiv2`) are given to the generator so that the schema resolves; they hold
field options only, and nothing of them reaches a pack.

## What this pack does not express

- `map` fields: no line addresses an entry by its key.
- `bytes` and the fixed-width integer types, single or repeated: no transform yields them.
- A value below path depth 6, and a message type that contains itself: the walk stops where a
  message type would stand inside itself, through a repeated field as through a single one.
- An unmapped field of an item: items carry no residue (engine-spec 0.7).
- The content of a message with no mappable field: its kind is kept, its fields are not.
- Which member of a nested `oneof` is set: each member's fields are plain `field` lines of the kind
  or of the group. An item is not decoded by a discriminator (0.7 has no `when` inside a group).
- Enum names: an enum is carried as its number; the module key's meaning lists the names.
- `google.protobuf.Timestamp`: carried as two raw integer keys (seconds, nanos); no transform joins them into `time_ms`.
