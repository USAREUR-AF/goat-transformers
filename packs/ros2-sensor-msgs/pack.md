# ros2-sensor-msgs

ROS 2 `sensor_msgs` messages as the JSON of a rosbridge `publish` operation. Generated by
`tools/gen/ros2msg2pack.py` from the .msg files of the package (and the files
they refer to); do not edit by hand, run `tools/gen/ros2-run.sh`.

## Why the `json` wire

Inside ROS 2 a message is serialized as CDR by the middleware (and stored so by
rosbag2). A program outside ROS most often meets it as the JSON that rosbridge
publishes. rosbridge writes a message as one JSON object: each field a member
under its .msg name, a nested message an object, an array a JSON array,
`uint8[]` and `char[]` a base64 string (protocol section 3.1),
`builtin_interfaces/Time` and `Duration` an object `{sec, nanosec}`, and a float
that is NaN or infinite `null`. Every one of those maps to the `json` wire
(engine-spec 0.5, 0.7) with no addition to the pack language, for every message
of the package. CDR on the `bits` wire is not written: a CDR payload carries no
type, so no `when` can tell one message from another and each message would be
a format of its own; and a message with a string or an unbounded array places
every later field at an offset that depends on that length and its alignment,
which `layout sequential` has no line for (`align` is relative to the field
before it, not to a variable start).

## Message convention

A message is one rosbridge `publish` operation (protocol v2.1.0, section 4.3.3)
that carries the optional `type` member in the full notation of section 4.1:

```
{"op":"publish","topic":"<topic>","type":"sensor_msgs/msg/<Name>","msg":{<message>}}
```

- `op` must be `publish` (a common `when`); it is written on encode.
- `type` selects the kind; it is written on encode. The short notation
  `sensor_msgs/<Name>`, which rosbridge also accepts, selects no kind (`no-kind`).
  A `publish` the server sends to a subscriber has no `type`: the receiver adds
  it from its subscription before decoding.
- `topic` is the raw key `ros2sensor.topic`.
- Other members of the operation (`id`, `qos`, `latch`, `queue_size`) and any
  member of `msg` the pack does not map are residue when they are scalars or
  objects of scalars, and are written back after the mapped members.
- On encode for an entity from another format, the kind is the first, in the
  order below, whose `requires` keys the entity holds. Each kind requires its
  first key (a message with no field requires `ros2sensor.topic`).

## Shared-model keys

Three fields of `sensor_msgs/msg/NavSatFix` are bound to `core` keys. The
evidence is the comment text of `sensor_msgs/msg/NavSatFix.msg` at the commit in
`PROVENANCE.md` (Apache License 2.0), quoted in part:

| Wire field | Model key | Evidence in NavSatFix.msg | Note |
|---|---|---|---|
| `msg.latitude` (float64) | `lat` (deg, WGS 84) | file header: "Specified using the WGS 84 reference ellipsoid"; field: "Latitude [degrees]. Positive is north of equator" | same frame, unit and sign |
| `msg.longitude` (float64) | `lon` (deg, WGS 84) | "Longitude [degrees]. Positive is east of prime meridian" | same frame, unit and sign |
| `msg.altitude` (float64) | `hae` (m above the WGS 84 ellipsoid) | "Altitude [m]. Positive is above the WGS 84 ellipsoid (quiet NaN if no altitude is available)" | ellipsoidal height, not mean sea level; rosbridge writes the NaN as `null`, which decodes to an absent `hae` |

Kind `nav_sat_fix` requires `lat lon`, so an entity from another format with a
position is encoded as a NavSatFix.

Not bound, and why:

- `header.stamp` (`sec`, `nanosec`): the file says it is "the ROS time for this
  measurement", which may be simulation time and is not stated as UTC; it is
  also two fields where `time_ms` is one. Raw keys.
- `position_covariance` (ENU, m^2, row-major 3 by 3) and
  `position_covariance_type`: `ce` and `le` are circular and linear errors, a
  different quantity from a covariance matrix; deriving them would need a
  confidence level the message does not state. Raw keys.
- `status.status`, `status.service`: no shared key holds a fix quality or a
  constellation set. Raw keys.
- `header.frame_id`: the antenna's frame on the vehicle, not an identity of the
  vehicle; not `uid`. Raw key.
- No other message of the package states a geodetic frame. `sensor_msgs/msg/TimeReference`
  carries a time from an external source with no stated time base; raw keys.

## Validity flag not applied

nav_sat_fix: NavSatStatus `status` below 0 (-1 no fix, -2 not set, the default) means the position is not valid. The pack keeps the flag as a raw key and binds the position whatever it says: a message whose
flag says there is no fix converts with the coordinates it carries (often 0, 0), as if they were a
position. The pack language has no gate for a JSON or protobuf member yet (asked of gt-lang); until
it has, a consumer must read the flag. Bit-level packs of the same messages (PX4) read the shared
keys only when the flag says so.

## Not mapped, and why

| What | Why |
|---|---|
| Constants (`uint8 STATUS_FIX = 0` and the like), 50 in this package | the pack language has no line that names a constant of a field; the value of the field is carried as a number |
| Default values in the .msg (NavSatStatus.status -2) | not written on encode: rosbridge fills a field the `msg` omits with its default (protocol 4.3.3), so an absent key needs no value |
| Length of a fixed array and bound of a bounded one (CameraInfo.k float64[9], CameraInfo.p float64[12], CameraInfo.r float64[9], Imu.angular_velocity_covariance float64[9], Imu.linear_acceleration_covariance float64[9], Imu.orientation_covariance float64[9], MagneticField.magnetic_field_covariance float64[9], NavSatFix.position_covariance float64[9]) | a `json` group has no `count` (engine-spec 0.7); any number of items decodes and encodes, and a sender that writes another number is not refused |
| NaN and infinite floats | rosbridge writes them `null`; `null` is absent (engine-spec 0.5), so the key is absent and nothing is written back |
| `uint8[]` and `char[]` sent as a list of numbers | rosbridge accepts that from a client (protocol 3.1) but writes base64; the pack reads the base64 string only, and a list there is `transform-decode` |
| Members inside an array item that the .msg does not define | engine-spec 0.7: items carry no residue |
| PNG, CBOR and fragment encodings of the protocol (sections 3.2 to 3.5) | other byte forms of the operation; the pack reads JSON text |

## Vectors

`vectors/gen-rt-<kind>.json`: one round trip per kind, every field of the
message present, two items in each unbounded array outside a group and one
inside, the stated number in a fixed or bounded one, and an `id` member as
residue. `gen-edge-*` and `gen-err-*` are edge and error cases, each naming the
rule it rests on in `source`; `gen-x-*` convert to geojson. 31 vector files.
`packs/geojson/vectors/gen-geojson-to-ros2-sensor-msgs-*.json` convert from geojson.
Expected text is written by the generator from the .msg field order and checked
by its own json-wire codec; no engine produced it.
