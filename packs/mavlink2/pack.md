# Pack: mavlink2

MAVLink 2 frames carrying the `common.xml` message set (with the files it
includes, `standard.xml` and `minimal.xml`). Public. Generated by
`tools/gen/mavlink2pack.py` from `https://github.com/mavlink/mavlink` at commit `12c898d88ce18d24e8caf6338596e98c5005bc97`;
do not edit `pack.def`, `model/mavlink.def`, this file or the vectors by hand.
I/O is hex text (`spec/engine-spec.md`, bits wire).

Status: Built. Generated and checked by the generator's own reader; every engine
runs every vector in `vectors/` in the conformance suite.

## Layout

`wire bits`, `bit_order lsb`, `word_bytes 1`. A locator is `0:<bit offset>:<len>`
counted from the first bit of the STX byte.

| Part | Bytes | Locator | In the pack |
|---|---|---|---|
| STX | 1 | `0:0:8` | common `when` = 253 (0xFD) |
| LEN | 1 | `0:8:8` | per-kind `when` = full payload length |
| INCOMPAT | 1 | `0:16:8` | not mapped |
| COMPAT | 1 | `0:24:8` | not mapped |
| SEQ | 1 | `0:32:8` | `mavlink.seq` |
| SYSID | 1 | `0:40:8` | `mavlink.sysid` |
| COMPID | 1 | `0:48:8` | `mavlink.compid` |
| MSGID | 3, little-endian | `0:56:24` | per-kind `when` = message id |
| PAYLOAD | LEN | from `0:80` | the kind's `field` lines |
| CRC | 2 | after the payload | not mapped |

One `kind` per message, named by the message name in lower case, in message-id
order. Payload fields sit at their MAVLink 2 wire offsets: base fields in
descending type-size order (stable), then extension fields in declaration order.
The generator confirms its field order by computing each message's CRC_EXTRA and
comparing six of them with the values the protocol fixes.

## What is mapped

| MAVLink type | Transform | Model type |
|---|---|---|
| `uint8_t` `uint16_t` `uint32_t` `uint64_t` | `uint` | int |
| `int8_t` `int16_t` `int32_t` `int64_t` | `twos` | int |
| `float` | `f32` | float |
| `double` | `f64` | float |
| `char[n]` | `ascii` over `8n` bits | string |
| other `type[n]`, n of 2 to 8 | one line per element, keys `…_0`, `…_1`, … | as the element |
| `int32_t` degE7 named `lat` or `lon`, with no `invalid` value declared | `sscale:1/10000000` | float, core `lat` / `lon` |

Every other value is raw: the integer or float on the wire, in the unit the
definition states, which `model/mavlink.def` records in the key's unit column.

### Key names

A key is `mavlink.<field name>` with the unit appended when the field declares
one and the name does not already end with it (`mavlink.alt_mm`,
`mavlink.time_boot_ms`). Unit text is lower-cased; `/` becomes `_per_`, `%`
becomes `pct`, `*` becomes `_x`. One key is shared by every message whose field
has that name with the same type class (int, float, string), units and enum.
When the uses of a name disagree, every use takes the message name as a prefix
(`mavlink.<message>_<field>…`). 147 fields are named that way:

| Reason | Fields |
|---|---|
| different enums | 78 |
| different types | 58 |
| same name as a frame-header key | 11 |

### Core keys

15 kinds map core `lat` and `lon`: `gps_raw_int`, `global_position_int`, `global_position_int_cov`, `hil_state`, `hil_gps`, `hil_state_quaternion`, `gps2_raw`, `terrain_request`, `terrain_data`, `terrain_report`, `follow_target`, `gps_input`, `camera_image_captured`, `camera_tracking_geo_status`, `utm_global_position`.
The position is the one the message reports, which is not always the sending
vehicle's: `terrain_request`, `terrain_data` and `terrain_report`
carry a terrain grid point, `follow_target` a target, `camera_image_captured` the
camera at capture time.
`terrain_check` has no field but `lat` and `lon`; they stay raw there so the kind has a raw
key to require, otherwise any entity with a position would encode as that kind.

Left raw on purpose:

- degE7 fields that are not named `lat` / `lon` or that declare an `invalid`
  value (36 fields, for example `latitude`, `lat_int`, and `lat` of `adsb_vehicle`,
  `ais_vessel`, `global_position_sensor`, where INT32_MAX means unknown and would
  decode to 214.7483647 degrees).
- UTC epoch times in microseconds (`time_unix_usec`, `time_usec`, `time_utc`):
  core `time_ms` is an integer and the only scaling transforms yield float; a
  64-bit microsecond count scaled by 0.001 is not exact in a double.
- Altitude. MAVLink `alt` fields are above mean sea level; core `hae` is above
  the WGS84 ellipsoid.
- Speed, course, heading and velocity components (`vel`, `cog`, `hdg`, `vx`…):
  the reference frame is in the description text, not in the units, and most
  declare an `invalid` value (UINT16_MAX).

### `requires`

Each kind requires up to 6 of its own raw keys, the ones used by the fewest
kinds, so encoding an entity that came from another format selects a kind only
when the entity holds those `mavlink.` keys. No kind requires a core key, so a
GeoJSON or CoT entity selects no kind (`no-kind`).
For 50 kinds the required keys are all shared with at least one other kind
that maps every one of them; an entity built from such a kind's keys with its
kind cleared selects the first qualifying kind in id order: `param_request_read`, `param_request_list`, `gps_status`, `scaled_imu`, `scaled_pressure`, `attitude`, `local_position_ned`, `mission_request_partial_list`, `mission_write_partial_list`, `mission_request_list`, `mission_clear_all`, `set_gps_global_origin`, `gps_global_origin`, `safety_set_allowed_area`, `safety_allowed_area`, `attitude_quaternion_cov`, `rc_channels_override`, `command_cancel`, `local_position_ned_system_global_offset`, `hil_state`, `hil_rc_inputs_raw`, `global_vision_position_estimate`, `vision_position_estimate`, `vicon_position_estimate`, `optical_flow_rad`, `file_transfer_protocol`, `hil_optical_flow`, `scaled_imu2`, `log_data`, `log_erase`, `log_request_end`, `gps_rtk`, `gps2_rtk`, `scaled_imu3`, `terrain_check`, `scaled_pressure2`, `att_pos_mocap`, `set_actuator_control_target`, `actuator_control_target`, `scaled_pressure3`, `home_position`, `set_home_position`, `logging_data`, `logging_data_acked`, `logging_ack`, `param_ext_request_read`, `param_ext_request_list`, `canfd_frame`, `supported_tunes`, `wheel_distance`.

## Known limits

- **Truncated payloads.** MAVLink 2 senders drop trailing zero bytes of the
  payload and set LEN to the shorter length. Each kind matches only LEN = the
  full length, so a truncated frame decodes as `no-kind`. Reading one needs the
  future framed-binary wire (a length-prefixed payload that is zero-extended).
- **CRC.** Decode does not verify the checksum and encode does not write it.
  Encode output is the header and payload up to the last mapped byte; it is not
  a transmittable frame until a framer adds truncation and the CRC (with the
  message's CRC_EXTRA). Input that carries the CRC or a signature decodes: bytes
  after the last mapped bit are ignored.
- **Short output.** In 25 kinds the payload ends in unmapped array fields, so
  encode output is shorter than `10 + LEN` bytes: `gps_status`, `attitude_quaternion_cov`, `vicon_position_estimate`, `file_transfer_protocol`, `log_data`, `gps_inject_data`, `encapsulated_data`, `att_pos_mocap`, `resource_request`, `autopilot_version`, `gps_rtcm_data`, `v2_extension`, `memory_vect`, `setup_signing`, `logging_data`, `logging_data_acked`, `debug_float_array`, `actuator_output_status`, `tunnel`, `canfd_frame`, `event`, `radio_rc_channels`, `open_drone_id_basic_id`, `open_drone_id_authentication`, `open_drone_id_message_pack`.
- **Unmapped bits do not round-trip.** The bits wire has no residue: INCOMPAT,
  COMPAT and unmapped arrays are written as zero.
- **`invalid` values.** A field's `invalid` attribute (a value that means
  unknown) is not interpreted; the key holds the number.
- **Text.** `ascii` refuses bytes outside 0x20..0x7E, so a `char[n]` field that
  holds UTF-8 or binary data fails to decode. Trailing NULs are dropped; an
  all-NUL field is the empty string, present.
- **`uint64_t`** is mapped with `uint` to the model type int; a value of 2^63 or
  above is the negative model integer with the same bits (engine-spec 0.5, ruling 2).
- **Enums and bitmasks** are carried as their integer.

## Vectors

`vectors/rt-<id>-<kind>.json`: one same-format round trip per kind. The input
is the frame as the encoder writes it (no CRC, unmapped arrays absent or zero),
so input and expected output are identical. Values are inside each field's
range; floats are multiples of 0.25 or 0.125; every other `uint64_t` sample has
its top bit set.

`vectors/x-NN-<kind>-to-geojson.json`: 5 full frames with a correct CRC,
converted to GeoJSON. Expected output: `coordinates` = `[lon, lat]` in degrees
(wire value / 10^7), `properties` empty because `geojson` carries no other key
this pack maps.
