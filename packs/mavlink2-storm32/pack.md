# Pack: mavlink2-storm32

MAVLink 2 frames carrying the messages that the dialect file `storm32.xml` defines
itself. Public. Generated by `tools/gen/mavlink2pack.py --dialect storm32` from
`https://github.com/mavlink/mavlink` (`message_definitions/v1.0/storm32.xml`) at commit `12c898d88ce18d24e8caf6338596e98c5005bc97`;
do not edit `pack.def`, `model/mavlinkstorm32.def`, this file or the vectors by hand.
I/O is hex text (`spec/engine-spec.md`, bits wire). Source, hashes and license:
`PROVENANCE.md`.

Status: Built. Generated and checked by the generator's own reader; every engine
runs every vector in `vectors/` in the conformance suite.

## Scope: the dialect's own messages

`storm32.xml` includes `ardupilotmega.xml`, `common.xml`, `standard.xml`, `minimal.xml`, `uAvionix.xml`, `icarous.xml`, `loweheiser.xml`, `cubepilot.xml`, `csAirLink.xml`. The pack holds only the messages `storm32.xml`
itself defines; the messages of the included files are in the pack of the file
that defines them (`mavlink2` for `common.xml`, `standard.xml` and `minimal.xml`,
`mavlink2-<dialect>` for a dialect). The included files are read only to check
that every message id and every message name of the whole set is unique.

So no message id occurs twice inside the pack, and a message is described by
exactly one pack in the repository. A system that speaks the dialect loads
`mavlink2` and the packs of every file the dialect includes, and names the pack
of the message when it converts. A frame of an included message is `no-kind` in
this pack.

## Layout

The frame is the one `packs/mavlink2/pack.md` describes: `wire bits`, `bit_order lsb`,
`word_bytes 1`, locators `0:<bit offset>:<len>` from the STX byte, a common `when`
on STX = 253, and per kind a `when` on MSGID (`0:56:24`) and on LEN (`0:8:8`) = the
full payload length. The frame-header keys `mavlink.seq`, `mavlink.sysid`,
`mavlink.compid`, `mavlink.incompat_flags` and `mavlink.compat_flags` are those of
module `mavlink`, so they carry over between every
MAVLink pack. Payload keys are in this pack's own module `mavlinkstorm32`.
Payload fields sit at their MAVLink 2 wire offsets: base fields in descending
type-size order (stable), then extension fields in declaration order. The
generator confirms the order by computing CRC_EXTRA and the payload length of
12 messages and comparing them with the values in the C library that the
MAVLink project generates from the same definitions (`PROVENANCE.md`).

## What is mapped

| MAVLink type | Transform | Model type |
|---|---|---|
| `uint8_t` `uint16_t` `uint32_t` `uint64_t` | `uint` | int |
| `int8_t` `int16_t` `int32_t` `int64_t` | `twos` | int |
| `float` | `f32` | float |
| `double` | `f64` | float |
| `char[n]` | `ascii` over `8n` bits | string |
| other `type[n]`, n of 2 to 8 | one line per element, keys `…_0`, `…_1`, … | as the element |
| `int32_t` degE7 named `lat`, and `lon` or `lng`, both in one message, with no `invalid` value declared | `sscale:1/10000000` | float, core `lat` / `lon` |

Every other value is raw: the integer or float on the wire, in the unit the
definition states, which `model/mavlinkstorm32.def` records in the key's unit column.

### Arrays of more than 8 elements

2 array fields (488 bytes of payload) are mapped one key per element as the
shorter arrays are, keys `<name>_0` to `<name>_<n-1>`. Their keys are named in
a pass after every other key, so they never change a key the shorter-array rule
gives: a field's element keys are shared with other messages only when every
long use agrees on type class, units and enum and every key name that already
exists has the same meaning; otherwise the field takes its message name as a
prefix. Byte blobs (`uint8_t[n]` holding a file chunk, RTCM data, a URI) are
carried byte by byte as integers 0..255; the model has no byte-string type a
`bits` transform yields.

| Message | Field | Type | Keys |
|---|---|---|---|
| FRSKY_PASSTHROUGH_ARRAY | packet_buf | `uint8_t[240]` | `mavlinkstorm32.packet_buf_0` … `_239` |
| PARAM_VALUE_ARRAY | packet_buf | `uint8_t[248]` | `mavlinkstorm32.packet_buf_0` … `_247` |

### Key names

The rules of `packs/mavlink2/pack.md` (Key names), within this dialect: a key is
`mavlinkstorm32.<field name>` with the unit appended when the field declares one and
the name does not already end with it; one key is shared by every message of the
dialect whose field has that name, type class, units and enum; otherwise every use
takes the message name as a prefix. 4 fields are named that way:

| Reason | Fields |
|---|---|
| different enums | 4 |

### Core keys

No message of `storm32.xml` has a latitude and a longitude field that bind core keys,
so no kind maps a shared key and the pack converts to no other format.

Not bound to a shared key, for the reasons `packs/mavlink2/pack.md` gives:
altitude (MAVLink altitudes are above mean sea level or relative, core `hae` is
above the ellipsoid), epoch times in microseconds, and speed, course and velocity
(the frame is stated in description text, not in the units).

### `requires`

Each kind requires up to 6 of its own raw keys, the ones used by the fewest
kinds of this pack. No kind requires a core key, so a GeoJSON or CoT entity, or an
entity decoded by another MAVLink pack, selects no kind here (`no-kind`).

## What is not mapped

- CRC (2 bytes after the payload) and the 13-byte signature of a signed frame.
  A field line with the `optional` option could read them, but encode writes
  every field line of the kind whether its key is present or not (vector
  `06-optional-truncated-roundtrip-writes-whole-message` of
  `conformance-rules-bits`), so every unsigned frame would gain 13 zero bytes
  and every frame from another format a CRC of zero. Mapping them needs a rule
  that computes the checksum and one that writes a part only when a flag is set.
- Enum and bitmask values are carried as their integer; enum names are not
  taken into the model.

## Known limits

Those of `packs/mavlink2/pack.md` (Known limits) hold here unchanged: truncated
payloads (LEN shorter than the full length) are `no-kind`; the CRC is neither
checked nor written; an `invalid` value is
carried as its number; `ascii` refuses bytes outside 0x20..0x7E; `uint64_t` values
of 2^63 or above are the negative model integer with the same bits.

## Message status in the source

The definition marks 4 messages as work in progress, liable to change in a
later commit: `autopilot_state_for_gimbal_device_ext`, `qshot_status`, `param_value_array`, `mlrs_radio_link_flow_control`.
The pack maps them as the pinned commit defines them.

## Vectors

`vectors/rt-<id>-<kind>.json`: one same-format round trip per kind, computed by
the generator's own encoder (no CRC; every other frame has COMPAT = 1), so input
and expected output are identical.
