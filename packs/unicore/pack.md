## The message

`wire bits`, `bit_order lsb`, `word_bytes 1`; hex text. One UNI binary frame
without its sync bytes (0xAA 0x44 0xB5) and its CRC-32; every number is
little-endian. The header is 21 bytes:

| Bytes | Field | In the pack |
|---|---|---|
| 0 | CPU idle | `unicore.header_cpuidle` |
| 1-2 | message ID | per-kind `when` |
| 3-4 | payload length in bytes | per-kind `when` |
| 5, 6 | time reference, time status | `unicore.header_timeref`, `unicore.header_timestatus` |
| 7-8, 9-12 | week, time of week | `unicore.header_wno`, `unicore.header_tow` |
| 13-16, 17, 18, 19-20 | version, reserved, leap seconds, delay | `unicore.header_*` |
| 21 … | payload | the kind's `field` lines |

A framer adds the sync bytes and the CRC before sending and checks them on
receipt: CRC-32 (reflected polynomial 0xEDB88320, initial value 0) over the
sync bytes, the header and the payload, written little-endian after the
payload. That is the item "Layered wires and framing" of `docs/roadmap.md`.

Keys are `unicore.<message>_<field>` in lower case. A scale the source states is
applied; the source states no unit, so the module declares none (`-`).

### Core keys

None. The position messages (BESTNAV and the others like it) carry `lat` and
`lon` as doubles that pyunigps's own README treats as degrees, and a `datumid`
field that names the datum of each message. The source does not say which
`datumid` value is WGS 84, so no message can be shown to hold WGS 84
coordinates; binding `lat` and `lon` would need that value, and then a gate
(Version 0.17, `if <locator> <value>`) on `datumid`. The height these messages
give is above mean sea level (`hmsl`), not the ellipsoid, so it would not bind
`hae` either.

### `requires`

Each kind requires up to 3 of its own keys, so an entity from another format
selects a kind only when it holds them.
