# Pack: mavlink2-ardupilotmega

MAVLink 2 frames carrying the messages that the dialect file `ardupilotmega.xml` defines
itself. Public. Generated by `tools/gen/mavlink2pack.py --dialect ardupilotmega` from
`https://github.com/mavlink/mavlink` (`message_definitions/v1.0/ardupilotmega.xml`) at commit `12c898d88ce18d24e8caf6338596e98c5005bc97`;
do not edit `pack.def`, `model/mavlinkardupilotmega.def`, this file or the vectors by hand.
I/O is hex text (`spec/engine-spec.md`, bits wire). Source, hashes and license:
`PROVENANCE.md`.

Status: Built. Generated and checked by the generator's own reader; every engine
runs every vector in `vectors/` in the conformance suite.

## Scope: the dialect's own messages

`ardupilotmega.xml` includes `common.xml`, `standard.xml`, `minimal.xml`, `uAvionix.xml`, `icarous.xml`, `loweheiser.xml`, `cubepilot.xml`, `csAirLink.xml`. The pack holds only the messages `ardupilotmega.xml`
itself defines; the messages of the included files are in the pack of the file
that defines them (`mavlink2` for `common.xml`, `standard.xml` and `minimal.xml`,
`mavlink2-<dialect>` for a dialect). The included files are read only to check
that every message id and every message name of the whole set is unique.

So no message id occurs twice inside the pack, and a message is described by
exactly one pack in the repository. A system that speaks the dialect loads
`mavlink2` and the packs of every file the dialect includes, and names the pack
of the message when it converts. A frame of an included message is `no-kind` in
this pack.

## Layout

The frame is the one `packs/mavlink2/pack.md` describes: `wire bits`, `bit_order lsb`,
`word_bytes 1`, locators `0:<bit offset>:<len>` from the STX byte, a common `when`
on STX = 253, and per kind a `when` on MSGID (`0:56:24`) and on LEN (`0:8:8`) = the
full payload length. The frame-header keys `mavlink.seq`, `mavlink.sysid`,
`mavlink.compid`, `mavlink.incompat_flags` and `mavlink.compat_flags` are those of
module `mavlink`, so they carry over between every
MAVLink pack. Payload keys are in this pack's own module `mavlinkardupilotmega`.
Payload fields sit at their MAVLink 2 wire offsets: base fields in descending
type-size order (stable), then extension fields in declaration order. The
generator confirms the order by computing CRC_EXTRA and the payload length of
73 messages and comparing them with the values in the C library that the
MAVLink project generates from the same definitions (`PROVENANCE.md`).

### Core keys

The binding is the one `mavlink2` makes, for the same field semantics: an
`int32_t` field in degE7 that the definition names and describes as the
latitude or longitude, whose `invalid` value, if any, the pack states as `absent`.
A message binds only when it has
one latitude and one longitude field that qualify.
This dialect spells the longitude `lng`; it is treated as `lon`.
The position is the one the message reports:

| Kind | Fields | Position |
|---|---|---|
| `simstate` | `lat` / `lng` | the vehicle in the simulation environment (simulator state, not a measurement) |
| `rally_point` | `lat` / `lng` | a rally point sent to or read from the vehicle, not the vehicle |
| `ahrs2` | `lat` / `lng` | the vehicle, as the secondary attitude and heading filter estimates it |
| `camera_feedback` | `lat` / `lng` | the vehicle when the camera captured an image |
| `ahrs3` | `lat` / `lng` | the vehicle, as the third attitude and heading filter estimates it |
| `water_depth` | `lat` / `lng` | the vehicle when the water depth was measured |

Left raw: `DEEPSTALL.landing_lat`, `DEEPSTALL.landing_lon`, `DEEPSTALL.path_lat`, `DEEPSTALL.path_lon`, `DEEPSTALL.arc_entry_lat`, `DEEPSTALL.arc_entry_lon`. A field stays raw when its name is not `lat`, `lon` or `lng`,
when it declares an `invalid` value the pack cannot state, or when its
message has no qualifying partner field.

Not bound to a shared key, for the reasons `packs/mavlink2/pack.md` gives:
altitude (MAVLink altitudes are above mean sea level or relative, core `hae` is
above the ellipsoid), times that may be since boot, and speed, course and velocity
(the frame is stated in description text, not in the units).

### `requires`

Each kind requires up to 6 of its own raw keys, the ones used by the fewest
kinds of this pack. No kind requires a core key, so a GeoJSON or CoT entity, or an
entity decoded by another MAVLink pack, selects no kind here (`no-kind`).
For 19 kinds the required keys are all mapped by another kind too; an entity
built from such a kind's keys with its kind cleared selects the first
qualifying kind in id order: `fence_fetch_point`, `data16`, `data32`, `data64`, `rally_fetch_point`, `ahrs2`, `autopilot_version_request`, `gopro_get_request`, `device_op_read`, `device_op_write`, `esc_telemetry_1_to_4`, `esc_telemetry_5_to_8`, `esc_telemetry_9_to_12`, `osd_param_show_config`, `esc_telemetry_13_to_16`, `esc_telemetry_17_to_20`, `esc_telemetry_21_to_24`, `esc_telemetry_25_to_28`, `esc_telemetry_29_to_32`.

## Times

A field is bound to core `time_ms` (epoch milliseconds UTC) when its definition
states a time since the Unix epoch, or since a fixed UTC instant, and nothing
else; the transform is an integer scale of engine-spec 0.15:

| Kind | Field | Transform | The definition states |
|---|---|---|---|
| `camera_status` | `time_usec` | `uiscale:1/1000` | microseconds since the Unix epoch by the camera clock |
| `camera_feedback` | `time_usec` | `uiscale:1/1000` | microseconds since the Unix epoch of the image |

A microsecond count keeps whole milliseconds: decode rounds to the nearest
millisecond (half away from zero) and encode writes that millisecond times 1000,
so a frame whose count is not a whole number of milliseconds re-encodes rounded
(`vectors/tm-*.json`). The raw keys these fields had stay declared in the module.

## Values that mean unknown

A field whose definition declares an `invalid` value carries the option
`absent <raw value>[,...]` (engine-spec 0.9): the value decodes to no key, and
an entity without the key encodes the first raw value. 0 `field` lines of 0
fields carry it. The raw value is the field's bits as an unsigned integer:

| `invalid` | Raw value |
|---|---|
| `INT32_MAX`, `UINT16_MAX` and the other limits | the limit's bits (INT32_MAX: 2147483647) |
| a decimal number (`0`, `-1`, `-1000`) | its two's-complement bits for an integer, its IEEE bits for a float |
| a limit or a hex number on a float (`UINT16_MAX`, `0xFFFF`) | the IEEE bits of that number (65535.0) |
| `NaN` on a `float` / `double` | 2143289344,4290772992 / 9221120237041090560,18444492273895866368 (the quiet NaN, then with the sign bit) |
| `[v]` on an array | `v` on every element |
| `[v1,,v3,]` | `v1` on the first element, `v3` on the third |
| `[NaN:]` on a float array | NaN on every element |

`[NaN:]` means the whole array is unknown when the first element is NaN; the pack
states only that each NaN element has no value (a NaN is never a model value).
0 lines take two raw values (the NaNs); an input with the second re-encodes
with the first.

## What is not mapped

- CRC (2 bytes after the payload) and the 13-byte signature of a signed frame.
  A field line with the `optional` option could read them, but encode writes
  every field line of the kind whether its key is present or not (vector
  `06-optional-truncated-roundtrip-writes-whole-message` of
  `conformance-rules-bits`), so every unsigned frame would gain 13 zero bytes
  and every frame from another format a CRC of zero. Mapping them needs a rule
  that computes the checksum and one that writes a part only when a flag is set.
- Enum and bitmask values are carried as their integer; enum names are not
  taken into the model.

## Known limits

Those of `packs/mavlink2/pack.md` (Known limits) hold here unchanged: truncated
payloads (LEN shorter than the full length) are `no-kind`; the CRC is neither
checked nor written;
`ascii` refuses bytes outside 0x20..0x7E; `uint64_t` values
of 2^63 or above are the negative model integer with the same bits.

## Message status in the source

The pack maps them as the pinned commit defines them.

## Vectors

`vectors/rt-<id>-<kind>.json`: one same-format round trip per kind, computed by
the generator's own encoder (no CRC; every other frame has COMPAT = 1), so input
and expected output are identical.

`vectors/x-NN-<kind>-to-geojson.json`: 3 full frames with a correct CRC
(computed with the message's CRC_EXTRA), converted to GeoJSON. The expected
output is written by hand in the generator from the field values: `coordinates`
= `[lon, lat]` in degrees (wire value / 10^7), `properties` empty because
`geojson` carries no other key this pack maps.
