# ros2-px4-msgs

ROS 2 `px4_msgs` messages as the JSON of a rosbridge `publish` operation. Generated by
`tools/gen/ros2msg2pack.py` from the .msg files of the package (and the files
they refer to); do not edit by hand, run `tools/gen/ros2-run.sh`.

## Why the `json` wire

Inside ROS 2 a message is serialized as CDR by the middleware (and stored so by
rosbag2). A program outside ROS most often meets it as the JSON that rosbridge
publishes. rosbridge writes a message as one JSON object: each field a member
under its .msg name, a nested message an object, an array a JSON array,
`uint8[]` and `char[]` a base64 string (protocol section 3.1),
`builtin_interfaces/Time` and `Duration` an object `{sec, nanosec}`, and a float
that is NaN or infinite `null`. Every one of those maps to the `json` wire
(engine-spec 0.5, 0.7) with no addition to the pack language, for every message
of the package. CDR on the `bits` wire is not written: a CDR payload carries no
type, so no `when` can tell one message from another and each message would be
a format of its own; and a message with a string or an unbounded array places
every later field at an offset that depends on that length and its alignment,
which `layout sequential` has no line for (`align` is relative to the field
before it, not to a variable start).

## Message convention

A message is one rosbridge `publish` operation (protocol v2.1.0, section 4.3.3)
that carries the optional `type` member in the full notation of section 4.1:

```
{"op":"publish","topic":"<topic>","type":"px4_msgs/msg/<Name>","msg":{<message>}}
```

- `op` must be `publish` (a common `when`); it is written on encode.
- `type` selects the kind; it is written on encode. The short notation
  `px4_msgs/<Name>`, which rosbridge also accepts, selects no kind (`no-kind`).
  A `publish` the server sends to a subscriber has no `type`: the receiver adds
  it from its subscription before decoding.
- `topic` is the raw key `ros2px4.topic`.
- Other members of the operation (`id`, `qos`, `latch`, `queue_size`) and any
  member of `msg` the pack does not map are residue when they are scalars or
  objects of scalars, and are written back after the mapped members.
- On encode for an entity from another format, the kind is the first, in the
  order below, whose `requires` keys the entity holds. Each kind requires its
  first key (a message with no field requires `ros2px4.topic`).

## Shared-model keys

Six kinds of `px4_msgs` state a position in WGS 84. They are bound to `core`
keys where the .msg file states the datum, and to `hae` only where it states the
ellipsoid. The evidence is the comment text of the .msg files at the commit in
`PROVENANCE.md`, quoted in part:

| Kind | Wire fields | Model keys | Evidence |
|---|---|---|---|
| `sensor_gnss` | `latitude`, `longitude`, `altitude_ellipsoid` | `lat`, `lon`, `hae` | "GNSS receiver report, position in WGS84"; "[deg] Latitude", "[deg] Longitude"; "[m] Altitude above the WGS84 ellipsoid" |
| `vehicle_global_position` | `lat`, `lon`, `alt_ellipsoid` | `lat`, `lon`, `hae` | "Fused global position in WGS84"; "Latitude, (degrees)", "Longitude, (degrees)"; "Altitude above ellipsoid, (meters)" |
| `home_position` | `lat`, `lon` | `lat`, `lon` | "GPS home position in WGS84 coordinates"; "Latitude in degrees", "Longitude in degrees" |
| `aux_global_position` | `lat`, `lon` | `lat`, `lon` | "[deg] Latitude in WGS84", "[deg] Longitude in WGS84" |
| `target_gnss` | `latitude_deg`, `longitude_deg` | `lat`, `lon` | "Landing target GNSS position in WGS84 coordinates"; "[deg] Latitude", "[deg] Longitude" |
| `camera_capture` | `lat`, `lon` | `lat`, `lon` | "Latitude in degrees (WGS84)", "Longitude in degrees (WGS84)" |

Each of these kinds requires `lat lon`. An entity from another format with a
position is encoded as `aux_global_position`, the first of them in pack order.

Not bound, and why:

- `altitude_msl`, `alt` (AMSL) and `altitude_msl_m` are above mean sea level, not the
  ellipsoid, so they are not bound to `hae`.
- `RangingBeacon.lat`/`lon` state no datum; only its altitude type names WGS 84.
- `PositionSetpointTriplet` holds three setpoints, not one position. `OrbitStatus`
  and `VehicleCommand` positions depend on a frame field or a command number.
- `timestamp` is microseconds since the system started, not UTC, so it is not
  bound to `time_ms`.
- `SensorGnss.vel_north` and `vel_east` ("[m/s] North velocity", "[m/s] East
  velocity") have the meaning of `track.vel_north_ms` and `track.vel_east_ms`, but
  this batch binds positions only, and the generator binds `core` keys only. They are
  raw keys. `vel_down` points down, against `track.vel_up_ms`, and the json wire has
  no transform that negates a value.

## Validity flag not applied

home_position: `valid_hpos`; sensor_gnss: `fix_type` 0 and 1 are no fix; vehicle_global_position: `lat_lon_valid` and `alt_valid`; target_gnss: `abs_pos_updated` (a freshness flag rather than validity). The pack keeps the flag as a raw key and binds the position whatever it says: a message whose
flag says there is no fix converts with the coordinates it carries (often 0, 0), as if they were a
position. The pack language has no gate for a JSON or protobuf member yet (asked of gt-lang); until
it has, a consumer must read the flag. Bit-level packs of the same messages (PX4) read the shared
keys only when the flag says so.

## Vectors

`vectors/gen-rt-<kind>.json`: one round trip per kind, every field of the
message present, two items in each unbounded array outside a group and one
inside, the stated number in a fixed or bounded one, and an `id` member as
residue. `gen-edge-*` and `gen-err-*` are edge and error cases, each naming the
rule it rests on in `source`; `gen-x-*` convert to geojson. 278 vector files.
`packs/geojson/vectors/gen-geojson-to-ros2-px4-msgs-*.json` convert from geojson.
Expected text is written by the generator from the .msg field order and checked
by its own json-wire codec; no engine produced it.
