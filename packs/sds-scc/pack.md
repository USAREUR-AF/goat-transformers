## How a schema is read

Each member of a scalar type is a `field` line; members of nested objects have dotted paths.
An array is a `group` (engine-spec 0.7): items that are objects are walked as a message is,
with paths relative to the item; items of a scalar type are one `.` line. `allOf`, `oneOf`
and `anyOf` contribute the members of every branch, merged by name; `null` among the
types means the member may be absent. Types: string `string`, integer `int`, number
`float` (`int` when the schema states `multipleOf: 1`), boolean `bool`. A `date-time`
string is kept as text in its raw key, so it round-trips as written.

Residue (engine-spec 0.5): a scalar member no line maps, at any depth of nested objects, is
carried back; arrays no group maps, and anything inside them, are not.

Limits of this pack: objects nested deeper than 5 levels (an array counts as a level) are not mapped (set so that the pack, its module and its names file stay within 1 MB; at the default depth 8 they come to 9.5 MB). Such a place is in the table under Not mapped;
outside an array its scalars are residue and round-trip, inside an array they are dropped.

## The form: JSON, one root table

Space Data Standards (spacedatastandards.org) publishes each standard as a FlatBuffers
schema and, from it, a JSON Schema (draft 2019-09) in `lib/fbjson/<NAME>/main.fb.schema.json`.
The pack reads the JSON form that JSON Schema describes: one JSON object, the standard's
root table (`#/definitions/<NAME>`), with member names as the schema writes them.

- The FlatBuffers binary form of the same standard is not carried: it is a different wire
  (offset tables and vtables) that no wire type of this project reads.
- The `x-flatbuffer-*` annotations (FlatBuffers type names, enum numbers, defaults,
  `required`) are not read. A FlatBuffers default is not written by encode and not
  supplied by decode; an enum is its name as text, as the JSON Schema states it.
- A FlatBuffers union appears in the JSON Schema as a member whose schema is `anyOf` the
  branch tables, beside a member `<name>_type` that names the branch. The generator merges
  the members of every branch by name; `<name>_type` is a raw key of its own. Which
  branch a value belongs to is therefore read from `<name>_type`, not from the key.
- Several standards contain other standards (a table of one standard as a member or as
  the items of an array of another). Those are walked like any nested object and get
  keys of this pack's module; they are not keys of the other standard's module.

The CCSDS Navigation Data Messages that are also standards here (OMM, OEM, OPM, OCM, CDM,
TDM, RDM, ACM, AEM, APM) have their CCSDS XML form in the separate pack `ccsds-ndm-xml`.
That pack reads the CCSDS NDM/XML schema; these read the Space Data Standards JSON Schema,
whose member names, nesting and additions are its own. The two are separate formats and no
conversion between them is claimed.

Of the 299 standards at the pinned commit, 297 have a pack. XTC is not generated: it
restates XTCE (a telemetry and command database, not a message), which this project does
not build because of the reuse terms of the XTCE document. REC is not generated: it is a
collection whose records are a union of every other standard, so its keys would repeat
the other packs.

Five standards (SCC, CQR, SCN, LAM, REM) nest other standards deeply; at the generator's
default depth each pack would be 1.5 to 9.5 MB. They have a lower depth limit, stated
under "How a schema is read" with the reason, and every place it cuts is listed under
"Not mapped". Every other pack has the default limit.

## Evidence for the shared keys

- `uid`: bound in 70 standards to one member of the root table, and only where the
  schema's description of that member says it identifies the record or the one object the
  record is about: `ID` described as the (unique, stable) identifier of the record;
  `OBJECT_ID` in OMM, CAT, ACM and RDM described as the international designator of the
  object, and in OSM as the identifier of the object observed; `UID` in COT (the event
  identifier); `ENTITY_ID` in ETM and MPE (the identifier of the entity); in TMS, one
  state of a track, `TRACK_ID`, described as held constant over every state of the same
  track (its `ID` names the state record, which changes). The description is the
  evidence column of the table above. An `ID` or `OBJECT_ID` with no description,
  or one that names something other than the record (a country code, the object of a
  related record), is a raw key only.
- `lat`, `lon` in GNO, GNP, SEN and TMS, and `hae` in TMS only. GNP and TMS describe
  latitude and longitude as decimal degrees on WGS 84; GNO and SEN describe them as
  geodetic latitude and longitude in degrees, and the altitude beside them in the same
  table as metres above WGS-84. TMS describes `ALTITUDE_M` as metres above the WGS 84
  ellipsoid, which is `hae`; the GNO and SEN altitudes do not say ellipsoid, so they are
  raw keys.
- `speed_ms` and `course` in TMS only: `GROUND_SPEED_MPS` is described as the speed over
  ground in metres per second, `COURSE_DEG` as the course over ground in degrees true
  (the direction it moves, not the heading).

Not bound:

- `time_ms`. No string of these schemas states `format: date-time`; epochs say "ISO 8601
  UTC" in their description only. The `iso8601_ms` transform keeps milliseconds, while
  orbit epochs are often written to the microsecond, and encode writes the shared value
  first, so binding would shorten the epoch on a round trip; an epoch written without a
  `Z` or offset would fail the decode. Every epoch is a raw key and round-trips as text.
  TMS `EPOCH` (an RFC 3339 UTC epoch at a fixed millisecond, the instant the state is
  valid) would bind without loss; it waits for a way to state a date-time string the
  schema does not mark with `format`.
- Orbital positions. Orbital states and ephemerides are Cartesian positions in a stated
  reference frame (TEME, GCRF, ITRF and others), in km, not WGS-84 geodetic coordinates.
  Other geodetic positions (CRM, whose altitude is in kilometres and whose position is
  where a collection is asked for; ION, SIT, TBS, TXS, and the latitude of OBT, SEO, SWR
  and TRK) either do not state WGS 84 for both members or are not the position of the
  record's own subject; they are raw keys.
- `speed_ms`, `course` elsewhere: orbital velocities are vector components in km/s in a
  reference frame, not a ground speed and a direction.
