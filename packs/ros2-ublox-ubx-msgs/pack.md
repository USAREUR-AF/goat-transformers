# ros2-ublox-ubx-msgs

ROS 2 `ublox_ubx_msgs` messages as the JSON of a rosbridge `publish` operation. Generated by
`tools/gen/ros2msg2pack.py` from the .msg files of the package (and the files
they refer to); do not edit by hand, run `tools/gen/ros2-run.sh`.

## Why the `json` wire

Inside ROS 2 a message is serialized as CDR by the middleware (and stored so by
rosbag2). A program outside ROS most often meets it as the JSON that rosbridge
publishes. rosbridge writes a message as one JSON object: each field a member
under its .msg name, a nested message an object, an array a JSON array,
`uint8[]` and `char[]` a base64 string (protocol section 3.1),
`builtin_interfaces/Time` and `Duration` an object `{sec, nanosec}`, and a float
that is NaN or infinite `null`. Every one of those maps to the `json` wire
(engine-spec 0.5, 0.7) with no addition to the pack language, for every message
of the package. CDR on the `bits` wire is not written: a CDR payload carries no
type, so no `when` can tell one message from another and each message would be
a format of its own; and a message with a string or an unbounded array places
every later field at an offset that depends on that length and its alignment,
which `layout sequential` has no line for (`align` is relative to the field
before it, not to a variable start).

## Message convention

A message is one rosbridge `publish` operation (protocol v2.1.0, section 4.3.3)
that carries the optional `type` member in the full notation of section 4.1:

```
{"op":"publish","topic":"<topic>","type":"ublox_ubx_msgs/msg/<Name>","msg":{<message>}}
```

- `op` must be `publish` (a common `when`); it is written on encode.
- `type` selects the kind; it is written on encode. The short notation
  `ublox_ubx_msgs/<Name>`, which rosbridge also accepts, selects no kind (`no-kind`).
  A `publish` the server sends to a subscriber has no `type`: the receiver adds
  it from its subscription before decoding.
- `topic` is the raw key `ros2ubloxubx.topic`.
- Other members of the operation (`id`, `qos`, `latch`, `queue_size`) and any
  member of `msg` the pack does not map are residue when they are scalars or
  objects of scalars, and are written back after the mapped members.
- On encode for an entity from another format, the kind is the first, in the
  order below, whose `requires` keys the entity holds. Each kind requires its
  first key (a message with no field requires `ros2ubloxubx.topic`).

## Shared-model keys

The positions of three `ublox_ubx_msgs` navigation solutions are bound to `core` keys
with the json `scale` transform (engine-spec 0.15), and the raw integer keys stay at
the same places. The evidence is the comment text of the .msg files at the commit in
`PROVENANCE.md`, in this project's words:

| Kind | Wire fields | Model keys | Evidence |
|---|---|---|---|
| `ubx_nav_pvt` | `lat`, `lon` (int32); `height` (int32) | `lat`, `lon` with `scale:1/10000000`; `hae` with `scale:1/1000` | the file gives latitude and longitude in degrees scaled by 1e-7, and the height over the ellipsoid in millimetres, beside a separate height over mean sea level |
| `ubx_nav_pos_llh` | the same three | the same | the same field comments |
| `ubx_nav_hp_pos_llh` | the same three | the same | the same field comments; the high-precision parts (`lat_hp`, `lon_hp`, `height_hp`) refine each value and are raw keys, not added in |

None of these files names the datum. As for `ros2-ublox-msgs` (the KumarRobotics
package for the same receivers), the bindings take the receiver's configured datum,
WGS 84 by default; a receiver set to another datum reports positions that `lat`,
`lon` and `hae` do not hold.

Kind `ubx_nav_pvt` requires `lat lon`; `ubx_nav_hp_pos_llh` and `ubx_nav_pos_llh`
also require their own `itow`, so a position from another format becomes a
`ubx_nav_pvt`. `hmsl` is not `hae` and stays a raw key.

## Validity flag not applied

ubx_nav_hp_pos_llh: `invalid_lon`, `invalid_lat`, `invalid_height`; ubx_nav_pvt: `invalid_llh`, `gnss_fix_ok` and `gps_fix` 0. The pack keeps the flag as a raw key and binds the position whatever it says: a message whose
flag says there is no fix converts with the coordinates it carries (often 0, 0), as if they were a
position. The pack language has no gate for a JSON or protobuf member yet (asked of gt-lang); until
it has, a consumer must read the flag. Bit-level packs of the same messages (PX4) read the shared
keys only when the flag says so.

## Not mapped, and why

| What | Why |
|---|---|
| Constants (`uint8 STATUS_FIX = 0` and the like), 191 in this package | the pack language has no line that names a constant of a field; the value of the field is carried as a number |
| Default values in the .msg (none in this package) | not written on encode: rosbridge fills a field the `msg` omits with its default (protocol 4.3.3), so an absent key needs no value |
| Length of a fixed array and bound of a bounded one (CommsPortInfo.msgs uint16[4], SBASSvData.reserved_3 uint8[2], UBXMonComms.prot_ids uint8[4], UBXNavOrb.reserved_0 uint8[2], UBXNavSBAS.reserved_0 uint8[2], UBXNavSig.reserved_0 uint8[2], UBXRxmPmp.unique_word uint32[2], UBXRxmSpartnKey.reserved0 uint8[2], UBXSecUniqid.unique_id uint8[5]) | a `json` group has no `count` (engine-spec 0.7); any number of items decodes and encodes, and a sender that writes another number is not refused |
| NaN and infinite floats | rosbridge writes them `null`; `null` is absent (engine-spec 0.5), so the key is absent and nothing is written back |
| `uint8[]` and `char[]` sent as a list of numbers | rosbridge accepts that from a client (protocol 3.1) but writes base64; the pack reads the base64 string only, and a list there is `transform-decode` |
| Members inside an array item that the .msg does not define | engine-spec 0.7: items carry no residue |
| PNG, CBOR and fragment encodings of the protocol (sections 3.2 to 3.5) | other byte forms of the operation; the pack reads JSON text |

## Vectors

`vectors/gen-rt-<kind>.json`: one round trip per kind, every field of the
message present, two items in each unbounded array outside a group and one
inside, the stated number in a fixed or bounded one, and an `id` member as
residue. `gen-edge-*` and `gen-err-*` are edge and error cases, each naming the
rule it rests on in `source`; `gen-x-*` convert to geojson. 68 vector files.
`packs/geojson/vectors/gen-geojson-to-ros2-ublox-ubx-msgs-*.json` convert from geojson.
Expected text is written by the generator from the .msg field order and checked
by its own json-wire codec; no engine produced it.
